# 训练代理评估器材料采集与隔离验收协议

> **状态：已停止采用。** 项目不再预先采集人工标注的 25 个开发案例和 30 个隔离验收案例。当前方案改为使用真实运行自然产生的回合，由[多模态大模型任务评估器](vlm-task-evaluator.md)自动判断，并由人工审校关键结果。本文保留为历史决策记录，不得继续作为现场采集指令。

本文规定一次性真机材料的最低采集、标注和隔离方式。它只服务于训练代理评估器的开发与验收；所有材料永久禁止进入候选实现或候选策略训练。

## 完成判据

本任务只有在以下条件全部满足后才完成：

1. 在固定设备位姿、一个允许的 G1 基座位姿、标准操纵器起始状态和当前四路相机配置下，取得下表所列的有效材料。
2. 每个真机回合都保留四路原始视频、同步机器人状态、BrainCo 电流、控制器与硬件保护日志，以及采集配置版本和文件摘要。
3. 开发集与隔离验收集按本协议封存；隔离验收材料未向评估器开发者或编程智能体公开。
4. 所有有效案例完成事实标注和质量复核，无法形成可靠事实标签的案例作废并在原分组内补采。
5. 数据保管人记录最终位置、数量、缺失项和清单 SHA-256，并在 GitHub 任务中回填。

仓库当前没有可复用的历史原始视频、同步机器人状态或控制日志。因此，除非这些材料另存于仓库之外并通过本协议的完整性检查，否则应按全量新采集处理。

## 最小材料矩阵

初始计划为 55 个案例。数字是足以启动低成本原型验证的最低操作基线，不是统计意义上的零误报证明；任一类别缺少清晰代表时，只在该类别和原分组内补采。

| 事实场景 | 开发集 | 隔离验收集 | 预期结果 | 采集要点 |
| --- | ---: | ---: | --- | --- |
| 指定手指清晰接触并撤离 | 8 | 10 | `succeeded` | 至少一个主视角连续看清接触前、接触和撤离后；另一视角可交叉核对 |
| 近距离经过但未接触 | 3 | 4 | `failed` | 计划最小间隙取当前系统可可靠执行和看清的最小安全值；不得靠电流单独证明未接触 |
| 接触后未撤离 | 3 | 4 | `failed` | 记录在仍接触时结束；回合结束后的人工恢复动作不得写入该回合 |
| 错误手指接触 | 3 | 4 | `failed` | 非指定手指接触黄色按钮；指定手指不得同时接触 |
| 遮挡或画面模糊 | 2 | 2 | `indeterminate` | 使用可移除遮挡物或自然自遮挡，不改变相机安装和设备位姿；使接触或撤离事实确实不可判断 |
| 多模态证据冲突 | 2 | 2 | `indeterminate` | 由完整原始回合制作可追溯的受控故障注入副本；见下文 |
| 硬件保护或运行故障中止 | 2 | 2 | `aborted` | 只注入已知可安全停机的运行故障；不得为造样本主动制造碰撞或危险越界 |
| 运动前拒绝执行 | 2 | 2 | `abstained` | 通过缺失前置条件或入口拒绝测试触发，机器人不得开始运动 |
| **合计** | **25** | **30** |  | 其中验收集含 10 个清晰成功和 20 个非成功案例 |

隔离验收中 10 个清晰成功使 80% 召回率门槛对应至少 8 个 `succeeded`。20 个非成功案例全部不得被判为 `succeeded`。这只是当前验收集上的观察门槛；自主实验中出现的新边界案例必须加入下一版隔离验收集并重新发布评估器。

## 采集前冻结

数据保管人在第一次真机动作前完成以下事项：

1. 从模板生成 55 个 `episode_id` 和预定分组，不允许采集后根据结果在开发集与验收集之间移动案例。
2. 分组采用 `development` 和 `acceptance`。同一动作脚本、故障方式或连续重复序列的近重复案例不得跨组复制。
3. 记录以下版本或内容摘要：
   - G1 机体、左右手和四个逻辑相机标识；
   - 相机固件、分辨率、帧率、曝光模式和安装状态；
   - 设备位姿、G1 基座位姿和标准操纵器起始状态；
   - 相机内外参、机器人运动学和时间同步配置；
   - BrainCo 固件与电流采样配置；
   - 唯一控制入口、硬件保护配置、采集器和动作脚本版本。
4. 拍摄一段不属于任何案例的场景基准视频，并保存设备、机器人和相机安装照片。它们只用于判断采集期间环境是否发生变化。
5. 验证急停、人工观察、回合结束和安全恢复流程。故障样本仅允许使用已经验证会进入安全停止状态的故障注入。

相机安装、手部安装、设备位姿或标定发生变化时立即停止采集；变化前后的材料不得混为同一数据集版本。

## 每个真机回合的固定步骤

1. 扫描 `episode_manifest.csv` 中下一条未采集记录，确认其分组和目标场景。
2. 验证设备、基座、标准操纵器起始状态、四路相机、时间同步、唯一控制入口和急停均就绪。
3. 创建只属于该 `episode_id` 的目录并开始所有原始流记录。记录开始时间不得晚于候选或诊断动作开始时间。
4. 通过唯一控制入口运行一次预定动作；一个回合只包含一次接触机会。
5. 在接触、撤离、拒绝或中止后的稳定状态结束记录。不得把下一次尝试或恢复动作并入同一回合。
6. `failed` 或 `indeterminate` 案例在关闭记录后执行固定恢复；`aborted` 后暂停采集并由人检查；`abstained` 先修复前置拒绝原因。
7. 运行完整性检查并写入每个文件的 SHA-256。缺流、截断、时间范围不重叠或配置漂移时标记 `capture_invalid`，保留失败记录，并用同分组的新后缀补采。
8. 操作者只记录动作是否按计划执行和异常事件，不在现场给出任务结果标签。事实标注在采集完成后根据封存证据进行。

## 安全生成特殊案例

### 多模态证据冲突

不通过危险动作制造冲突。先取得一个完整、有效的原始回合，再复制为派生案例并只做一种受控故障注入：

- 将机器人状态时间戳整体平移到超过冻结同步容差；或
- 用同一对照块中相反事实回合的一路相机流替换对应流，同时保留来源 `episode_id` 和原始摘要。

原始回合保持只读。派生案例必须记录 `derived_from_episode_id`、变换工具版本、变换参数和变换前后摘要。开发集来源只能生成开发集派生案例；验收集来源只能由数据保管人在封存区内生成验收集派生案例。

### `aborted` 与 `abstained`

- `aborted`：在远离设备、低速且可安全停止的动作中，注入候选进程退出、控制心跳丢失或其他已验证的运行故障，确认控制入口先产生中止记录再进入安全停止。
- `abstained`：在运动前故意缺失一个冻结的就绪条件，使唯一控制入口拒绝创建动作回合。

禁止通过碰撞、自碰、超过关节极限或可能损坏设备的动作制造材料。

## 原始材料目录

大体积材料不得提交 Git。使用数据保管人控制的外部只读存储，目录结构至少为：

```text
evaluator-evidence-v001/
├── dataset_manifest.json
├── episode_manifest.csv
├── development/
│   ├── labels.csv
│   └── episodes/<episode_id>/
└── acceptance-sealed/
    ├── labels.csv
    └── episodes/<episode_id>/
```

每个 `episodes/<episode_id>/` 至少包含：

```text
camera_0.mp4
camera_1.mp4
camera_2.mp4
camera_3.mp4
camera_timestamps.csv
robot_state.csv
brainco_current.csv
controller_events.jsonl
capture_metadata.json
sha256.txt
```

允许换用无损保真的容器格式，但四路原始画面不得只保存拼接视频；所有流必须能通过同一单调时钟对齐。`capture_metadata.json` 引用冻结配置的摘要，不应逐回合复制并漂移配置。

当前 G1 数据面由三个物理相机流产生四个逻辑视角：头部相机的一张 `1280×480` 原始 JPEG 包含左右两个 `640×480` 视角，另外两个流分别来自左右腕相机。`scripts/record_evaluator_episode.py` 按接收字节原样保存三个物理 JPEG 流，并在元数据中声明头部左右视角的派生关系；这比拆分后重新编码为四段视频更接近原始证据。`camera_timestamps.csv` 保存每帧的来源时钟、序号和摘要。

工作站时钟不能默认等于 G1 机载时钟。记录器使用状态包中的 G1 组装时间与工作站接收时间估计偏移，在 `brainco_current.csv` 中同时保存原始本机接收时间和换算到 G1 时钟域的估计时间；`capture_metadata.json` 保存偏移量及其采样范围。若偏移范围在一个回合内明显漂移，该回合不得进入正式材料。

只读冒烟记录可使用：

```bash
PYTHONPATH=/home/loongge/TWIST2-master/unitree_sdk2/python_binding/build-py310/lib \
  /home/loongge/miniconda3/envs/lerobot/bin/python \
  scripts/record_evaluator_episode.py \
  --episode-id SMOKE-YYYYMMDD-static \
  --output-root /mnt/data-hdd/Shaka/evaluator-evidence-smoke
```

该记录器只创建 DDS reader 和 ZeroMQ subscriber；它没有命令 topic、策略调用或执行权限。正式材料仍需将控制器与硬件保护事件接入同一个 `controller_events.jsonl`，不能把记录器自身的零写入事件当作完整控制日志。

调用运行器需要按候选的实际结束时间控制录制时，使用显式生命周期握手模式：

```bash
python scripts/record_evaluator_episode.py \
  --episode-id INVOCATION-ID \
  --output-root /path/to/evidence \
  --lifecycle-handshake \
  --post-roll-s 1.0
```

握手模式不使用 `--duration-s` 推测候选时长。记录器只有在隐藏的 partial 调用目录、全部输出文件、三个 DDS reader、三路物理相机订阅以及每类观测的首个样本都可用后，才在 stdout 输出 `read_only_recorder_ready` JSON 行。调用运行器应等待该事件后再启动候选；候选结束并释放控制权后向记录器发送 `SIGTERM`。记录器输出 `read_only_recorder_stop_requested`，继续录制完整的 `--post-roll-s`，随后原子化发布调用目录并输出 `read_only_recorder_completed`。`SIGINT` 是操作中断，不能当作正常停止。

初始化或运行失败输出 `read_only_recorder_failed`，包含失败 `phase`、`ready` 和 `reason`。失败目录保持为 `.<episode-id>.partial`，其中 `recorder_lifecycle.jsonl` 保留同样的阶段信息；它不会被提升为完整调用证据。不指定 `--lifecycle-handshake` 时，原固定时长入口仍只在结束时输出单个结果 JSON。

## 事实标注

标注者先观察四路原始视频，再用机器人状态、运动学、时间戳和电流交叉核对。BrainCo 电流不得单独把案例标成接触或成功。

标注的是可观察事实，不是评估器应输出什么。`expected_result` 按以下优先级从事实字段机械派生：

1. 机器人运动前被入口拒绝：`abstained`。
2. 硬件保护、急停或运行故障在回合中止：`aborted`。
3. 接触、手指身份或撤离不可判断，或多模态证据冲突：`indeterminate`。
4. 指定手指清晰接触黄色按钮，随后可见接触结束并从设备撤离：`succeeded`。
5. 证据清晰但未接触、接触后未撤离，或仅错误手指接触：`failed`。

开发集可由一名标注者完成。隔离验收集的全部人工事实标签在评估器运行前冻结；所有人工标为 `succeeded` 的案例、所有评估器预测为 `succeeded` 的案例以及任何不确定或分歧案例，必须由第二名不知道评估器输出的复核者检查。分歧不能通过讨论强行二分类：应标为 `indeterminate`，或在原分组补采一个事实清晰的替代案例。

## 隔离方式

1. 数据保管人是唯一可以读取 `acceptance-sealed` 原始材料和标签的人。
2. 评估器开发者和编程智能体只能访问开发集、字段合同和验收门槛，不能访问验收案例、标签、缩略图、逐案例输出或文件名中的答案线索。
3. 验收时，开发者提交版本化、不可修改的评估器包。数据保管人在封存环境运行它，只返回聚合结果：各输出数量、清晰成功召回率、假阳性数量、无效处理数量和门槛是否通过。
4. 未通过时不得开放失败案例调参。应使用开发集或另采开发材料修改评估器；同一验收集最多用于一个待发布版本的最终一次验收。需要再次验收时新建隔离集版本。
5. 发布记录同时绑定评估器摘要、数据集清单摘要、相机与标定摘要。任一绑定项变化，原验收失效。

## 质量检查与验收计算

有效案例必须同时满足：四路视频可解码；状态与日志覆盖完整回合；时间戳可对齐；所有必需版本已记录；摘要匹配；事实标签无未解决分歧。

验收计算只使用有效的隔离案例：

- 假阳性：`expected_result != succeeded` 且评估器输出 `succeeded`。必须为 0。
- 清晰成功召回率：清晰 `succeeded` 案例中评估器输出 `succeeded` 的比例。10 个清晰成功中至少 8 个。
- 所有证据不足或冲突案例必须输出 `indeterminate`。
- `aborted` 和 `abstained` 必须保持独立语义，不得计作 `failed`。
- 每个输出必须能追溯到 `episode_id`、原始文件摘要、评估器版本和冻结配置版本。
